# Protocol notes

Findings from the real hub vs. the official docs.

No discrepancy between the docs and the hub has been found so far. Add each one with: date, message/bytes, expected (docs), observed (hub), firmware version.

## Confirmed by capture

First real Move Hub capture, 2026-11-13 (Web Bluetooth; Chrome on Linux/BlueZ per the operator, not recorded in the file): `packages/lwp3/fixtures/2026-11-13-move-hub-connect.txt`. Tests: `packages/lwp3/src/capture-2026-11-13.test.ts`. The hub firmware version was not read in this capture.

- Virtual port AB id is dynamic: the hub sent `09 00 04 10 02 27 00 00 01` (Attached Virtual I/O, port **0x10**, type 0x0027, from ports 0x00 + 0x01). Keep reading it from the event; never hardcode it.
- The Move Hub advertises the LWP3 service UUID: the `requestDevice` filter by service UUID alone found it in Chrome.
- Framing: in this capture every notification carried exactly one complete message (inferred: the probe logs all frames of one notification in the same synchronous pass, so they would share a timestamp; every rx frame here has a distinct one, 2+ ms apart, and no split error was logged), with no multi-message notifications and no fragmentation. Inconclusive in general (one short session), so `splitFrames` stays and the fragmentation TODO below stays.
- Right after connecting, and unrequested, the hub sends 0x04 Hub Attached I/O for every port: 0x00, 0x01 and 0x03 (external), the virtual 0x10, and the internal 0x32, 0x3A, 0x3B, 0x3C and 0x46. Layout and little-endian ioType/revisions match the decoder (ports 0x00/0x01: type 0x0027; 0x03: 0x0025; 0x32: 0x0017 RGB light; 0x3A: 0x0028 tilt; 0x3B: 0x0015 current; 0x3C: 0x0014 voltage). All revisions are valid BCD (`bcd: true`).
- Internal port 0x46 reports io type **0x0042**, which is not in `IoTypeId`. It decodes with the raw number. None of pylgbst (messages.py:287-297, DevTypes jump 63 to 71), node-poweredup (consts.ts:110-111, 65 to 71) or pybricksdev (bytecodes.py:724-727, 0x3F to 0x4B) defines a device type 0x42 (0x42 there is a hub kind / 0x42 Port Input Format Setup Combined message, unrelated), so it is not added to the constants. Unmodelled, purpose unknown.
- Hub properties: Enable Updates on Battery (0x06) raised no error; Request Update of Advertising Name returned `0D 00 01 01 06 "Move Hub"` and battery returned `06 00 01 06 06 61` (97 %), both operation Update (0x06).
- The hub answered the two battery requests (Enable Updates, then Request Update) with two Update messages. It is inconclusive which answered which, so whether Enable Updates produces an immediate Update is still TODO(hw).

Found in code (`rg "TODO\(hw\)" packages`):

- Two-byte length field (messages over 127 bytes): literal from doc 3.2 only; the reference libraries do not cover it (pylgbst and node-poweredup emit one byte).
- UX: the first tx is at +10.8 s, measured from when the chooser returned the device (hub-probe `startedAt`), so it covers GATT connect + service discovery; the hub may also have stopped advertising just before being chosen (operator unsure). TODO(hw): measure again (other OS, other adapter); long for kids 7+, may need a progress indicator.
- Write queue per-send timeout (default 1000 ms in `createWriteQueue`): tune on a real hub against the STOP < 200 ms budget.
- Notification framing: `splitFrames` splits one notification into several frames by length and does not buffer across notifications. TODO(hw): whether the Move Hub ever fragments one message across notifications (node-poweredup assumes not; the first capture saw none, see "Confirmed by capture").
- Web adapter advertisement filter (`WebBleTransport.requestDevice`): filters by the LWP3 service UUID only. Confirmed by capture that the Move Hub is found this way (see above).
- Web adapter write mode (`WebBleTransport.write`): uses write-without-response when the characteristic reports it, else write-with-response. Still unknown (the capture log does not record the write mode). TODO(hw): measure which mode the Move Hub supports and the STOP latency in each against the 200 ms budget. There is no retry in the transport by design: a failed write rejects and the hub layer decides.
- Web adapter write timeout (`writeTimeoutMs`, default 1000 ms): a timed-out write tears the link down (a stalled GATT op would make Chrome refuse the next one as "already in progress"). TODO(hw): (a) tune the timeout against the 200 ms STOP budget, and `urgentDeadlineMs` (default 150 ms): an urgent write enqueued behind a stalled in-flight write declares that write dead after at most that long, which tears the link down so the hub sees a disconnect (every urgent write also has its own deadline, `urgentDeadlineMs` after ITS enqueue: one still pending or in flight then is declared dead, so a multi-port STOP over a slow link cannot outlast it, and the waiting urgent writes that missed theirs are cancelled); (b) does the Move Hub stop its motors by itself when the BLE link drops? If yes, tearing the link down on a stall is also the safest STOP.
- Version values with non-BCD digits or bit 31 set: decode is lenient (`bcd: false`, raw Int32 kept); real hub behaviour untested.
- Advertising name longer than 14 bytes: decode tolerates it. Real hubs untested.
- Hub Attached I/O (0x04): endianness of ioType and revisions is not stated in doc 3.8; little-endian is now confirmed by capture (pylgbst hub.py:164, node-poweredup lpf2hub.ts:240 and pybricksdev messages.py:516 agree). Unknown ioType values are kept raw, never an error.
- Port Input Format Setup/Format (0x41/0x47): delta interval endianness not stated in doc 3.17/3.23 (LE assumed). Non-zero notify treated as enabled, matching pylgbst/pybricksdev; TODO(hw) confirm hub only sends 0/1.
- Port Value (Single) (0x45): value endianness not stated in doc 3.21 (LE assumed). Decode keeps `raw` because the size depends on the port mode; `readPortValue` needs the Value Format from Port Mode Information (0x44), not yet modelled.
- Port mode table (`packages/lwp3/src/io-modes.ts`): value layouts per io type and mode are 'derivado del layout' from pylgbst peripherals.py and node-poweredup src/devices (each entry cites file:line); pybricksdev has no per-device mode table. No real 0x45 value has been captured, and the hub's own Port Mode Information (0x44, value format) is not modelled, so TODO(hw): capture 0x22/0x44 replies per port and compare. Known conflicts and gaps: voltage full scale (pylgbst 9.6 V vs node-poweredup 9.615 V over raw 3893); tilt angle axis order and sign (node-poweredup negates x); tilt modes 1..7 are single-ref (pylgbst shares one class between the WeDo 0x22 and Move Hub 0x28 sensors, and its numbering of modes 1..3 differs from node-poweredup's 0x22 table); motor mode 0 (power) and 3 and the "short" current/voltage mode 1 are left out (width unknown). `decodeModeValue` requires the exact length, so a value still in flight from the previous mode is dropped, not misread.
- Port Value multi-port (several ports in one 0x45, doc 3.21): out of scope. Decode treats everything after the first port id as that port's `raw`, so a multi-port frame yields mixed bytes. Needs the modes of every port to split.
- Doc section numbers: the fetched doc lists Port Value (Single) as 3.21 and Port Input Format (Single) as 3.23 (the task brief said 3.20/3.21).
- The pylgbst vectors for 0x04/0x47/0x45 come from its mocked tests (test_hub.py:36-117), not hub captures.

- Port Output Command (0x81, doc 3.26/3.27) and Feedback (0x82, doc 3.32): `time` is Int16 (0..MAX_INT16) and `degrees` Int32 (1..MAX_INT32) in the doc. Encoder follows the doc. Decoder is lenient: node-poweredup writes time with `writeUInt16LE` (tachomotor.ts:115) and degrees with `writeUInt32LE` (tachomotor.ts:149), and pylgbst uses `<H`/`<I` (peripherals.py:463, 508), so the decoder reads time as u16 (0..65535) and degrees as u32, accepting 0 for both. Bytes are identical within the doc's ranges. TODO(hw): whether the hub accepts time above 32767 or degrees 0.
- 0x81 speed rule (doc 3.27): StartSpeed (0x07/0x08) takes -100..100 and 126 (HOLD; the doc says "0 implies 126"), but not 127. StartSpeedForTime (0x09) and StartSpeedForDegrees (0x0B) take -100..100 only. FLOAT and BRAKE cannot be requested through speed commands: "the user has to use either StartPower(0 or 127)". The encoder enforces this; the decoder accepts 126 and 127 in every speed field so the simulator tolerates apps that send them (node-poweredup `mapSpeed` keeps 127, utils.ts:16).
- 0x81 StartPower (0x01) and StartPower2 (0x02, synchronized virtual port only), doc 3.27: Int8 -100..100 (negative counter-clockwise), 0 = FLOAT, 127 = BRAKE. Modelled as `startPower`/`startPower2`. The STOP command is startup immediate, completion none, `startPower` 127: `07 00 81 <port> 10 01 7F`. pybricksdev bytecodes.py:1035-1036 names START_POWER/START_POWER_2; pylgbst defines them at peripherals.py:363-364 and passes 127 through `_speed_abs` (:380-384), but its `stop()` (:414) uses a timed command with time 0, and node-poweredup `stop()` writes direct mode 0x51 power 0 (basicmotor.ts:54). The decoder rejects power outside -100..100 and 127 as bad-field.
- 0x81 `GotoAbsolutePosition` speed is 1..100 in the doc (other speeds: -100..100, 126 hold, 127 brake). pylgbst sends virtual-port commands as the single-port id + 1 (peripherals.py:388-390) instead of using the Speed1/Speed2 form of 0x07; node-poweredup (tachomotor.ts:118) and pybricksdev (bytecodes.py:1040) use 0x08 like the doc.
- 0x81 sub-commands not modelled (0x05/0x06 acc/dec time, 0x0A/0x0C/0x0E synchronized variants, 0x14 preset encoder, 0x50 WriteDirect): decoded as `{sub: "unknown", subCommand, payload}`, not as an error, so the simulator can ignore or log them. `WriteDirectModeData` (0x51) keeps mode + raw data; RGB example literal in doc 6.1.
- Doc 6.2.3 (Calibrate example) lists the passcode "Calib-Sensor" with a last byte 0x77 where "r" (0x72) is expected; looks like a doc typo. Not used by the codec.
- 0x82 flags: decoded booleans for bits 0x01..0x10; the raw byte is kept and bits above 0x10 are not an error.
- Simulator motor model (`packages/simulator/src/hub/motor.ts`, `motors.ts`), all supuestos until a capture: speed at 100 % is `DEFAULT_MAX_DEG_PER_SEC` = 1000 deg/s (no ref states the Move Hub motor's no-load speed); constant speed, no acceleration or inertia (`useProfile`, `maxPower` and end states float/hold/brake are ignored); power is treated as speed; a command on one motor stops the other motor of a virtual-port command it interrupts; 0x81 on a non-motor port answers InvalidUse, an unmodelled sub-command CommandNotRecognized; direct mode data is accepted only as mode 0 + one signed byte (node-poweredup basicmotor.ts:28). Motor input modes 1 (speed, Int8) and 2 (position, Int32 LE) come from pylgbst peripherals.py:487-488/541-548 and node-poweredup tachomotor.ts:169; mode 0 (power) is not modelled. `stopMotorsOnLinkLoss` (default true) is the same open question as the "does the Move Hub stop its motors when the link drops" item above.
- Simulator sensor values (`SimulatedHub.setSensorMode`, `packages/simulator/src/hub/sensor-modes.ts`), 'derivado del layout': the simulated hub reports, for the (port, mode) the app subscribed to, the value set for that mode, encoded with the lwp3 mode table (count/width/signed; the delta interval is per component). Precedence: `setSensorMode` > raw `setSensor` (any mode, kept for byte-level tests) > rest defaults. supuestos, TODO(hw): rest defaults (tilt flat [0, 0]; color 255 = none; distance 10 inches = nothing in range, the real maximum is undocumented; mode 8 repeats modes 0 and 1); a mode the io type does not have gets the 0x47 reply and no value (a real hub may answer with an error); output-only modes cannot be set. The simulator page sets modes 0, 1 and 8 of the color & distance sensor together and mode 0 of the tilt sensor.
- Simulator startup/completion semantics (`packages/simulator/src/hub/motors.ts`), supuestos: startup "immediate" replaces the port's running and buffered commands (each reported 0x04 discarded if it asked for feedback, one report per port); "buffer" waits for the running command; the buffer holds one command and a second one is answered 0x10 busy/full (even without feedback request). Completion "feedback": 0x01 when the command starts, 0x0A when it ends with nothing buffered, 0x02 when it ends and a buffered one follows; commands that run until replaced (start speed/power, direct mode) are complete as they start (0x01 then 0x0A). A virtual-port command reports the virtual port id. TODO(hw): all of it, together with the 0x0A note above.
- STOP by frames needs a write latency budget (simulator measurements, `packages/simulator/src/stop.test.ts`): STOP is one urgent write per motor port, serialized, and the first one waits for the write in flight, so n ports take about (n + 1) * L for a per-write latency L. Otherwise every urgent write is bounded at `urgentDeadlineMs` (150 ms from its own enqueue) by link teardown: the write queue declares a write still pending or in flight at that point dead, the adapter drops the link and the hub (if it stops on link loss, which is the `stopMotorsOnLinkLoss` supuesto) stops. Three motors by frames fit that deadline up to L = 37 ms (4 * 37 = 148); at 45 ms the simulator stops everything at 150 ms through link loss. TODO(hw): measure L on the real hub (write-without-response vs with response); decide whether 150 ms is the right urgent deadline (a value up to ~190 ms would let 45 ms writes finish by frames and still fit 200 ms). TODO(hw): does the hub accept several LWP3 messages in ONE GATT write? If yes, a single-write STOP would remove the (n + 1) factor. Until then the hub layer (task 1.4) should prefer `startPower2` (127, 127) on the virtual AB port, which covers A + B in one frame (3 * L).
- STOP and link loss: on a stalled link `gatt.disconnect()` may not deliver LL_TERMINATE promptly, so the real hub may only notice the loss after the BLE supervision timeout (seconds). Link loss is therefore NOT a < 200 ms STOP guarantee on real hardware, and STOP by frames is the primary path. The simulator models this with `linkLossDetectionMs` (default 0, supuesto; `stop.test.ts` "STOP limit" runs it at 2000 ms and asserts the miss). TODO(hw): measure how long the Move Hub takes to notice a dead link and whether it stops its motors then. Mitigation for later layers: the runtime should prefer bounded commands (`startSpeedForTime` / `startSpeedForDegrees`) for kid-facing blocks, so that a lost link cannot leave the motors running forever.

- Hub sensors (`packages/hub`, `TiltSensor`, `ColorDistanceSensor`), 'derivado del layout', never captured: tilt mode 0 is exposed as the two signed bytes decode (x, y), with NO sign adjustment: pylgbst reads them as is, node-poweredup negates x (movehubtiltsensor.ts:29), so "which way is forward" is open (TODO(hw): tilt a real hub). Tilt mode 1 (`onOrientation`, state ids) is single-ref and its ids are not tabled. Color ids follow the LWP3 color table as pylgbst (peripherals.py:22-33) and node-poweredup (consts.ts:138-151) list it (0 black ... 10 white, 255 none); `onColor` drops a byte outside it. The sensor's rest values (255 = no color, distance max) are the simulator's supuesto. One input mode per port, so color, distance and light cannot be listened to together (mode 8 combines color and distance). TODO(hw): the combined input mode (0x42) and what the real sensor reports at rest.
- Hub LED, button and battery (`packages/hub`: `HubLed`, `HubButton`, `MoveHub.onBattery`), 'derivado del layout', never captured: the LED write is `81 <0x32> 10 51 <mode> <data>` (mode 0 = one color id, mode 1 = r g b), e.g. red = `08 00 81 32 10 51 00 09`; it follows both refs (node-poweredup hubled.ts:36,57 with device.ts:138; pylgbst peripherals.py:244-259). We send it startup "immediate" without feedback (0x10); both refs request feedback. Both refs also set the port mode (0x41) before the write; we do the same but do not wait for its 0x47. TODO(hw): is that setup needed, and what is the hub's answer to the direct write (the simulator answers 0x05 invalid use to a bad color or size, and a command that asked for feedback gets 0x82 in-progress then completed+idle like a motor command that runs until replaced; all supuesto). The LED takes the color-table ids (255 and 0 both turn it off per pylgbst). Button and battery updates reuse the hub property frames of the first capture's battery exchange (`05 00 01 <property> <operation>`); the hub's reply to Enable Updates is still the inconclusive point above.
- Hub layer (`packages/hub`), supuestos until a capture: (a) every setup 0x41 is answered by a 0x47 for the same port and mode (the first capture has no 0x41; the simulator echoes it); (b) feedback correlation is per port in send order: 0x02 completes the oldest; 0x04 settles the oldest and the "buffer" commands queued right behind it (the next "immediate" one displaced them and gets its own report); 0x10 rejects the newest as busy; 0x01 and 0x08 settle nothing; (c) a generic error (0x05) has no port, so it is attributed only when exactly one request of that type is pending and nothing of that type was written after it, else it is an `unattributed-error` event; a command settled locally (STOP, timeout) whose write reached the hub is assumed to draw one late report within 1 s, swallowed (a 0x04 any time in the window, a 0x02/0x0A only before the next command's own 0x01); a write cancelled in the queue draws none; (d) the Hub Attached I/O burst after connecting has no end marker, so `PortRegistry` is ready after 100 ms without a 0x04 (the capture's frames came 4-5 ms apart); (e) `stopAll` settles the feedback waiters of every port locally as "discarded" instead of waiting for 0x04 reports the hub may not send; and it never rejects (it returns `{ ok, errors }`); (f) motor commands are sent startup "immediate" with no acceleration profile, and timed/positioned ones end in brake (127); (g) a link loss clears the registry without detach events; (h) one input mode per motor port (`mode-conflict`): TODO(hw) whether the combined mode (0x42) can report position and speed together.
- Hub layer STOP timing (simulator, `packages/hub/src/move-hub.test.ts`): AB + an external motor on C = two urgent frames, 30 ms measured at L = 10 ms and 90 ms at L = 30 ms, matching 3 x L. A third motor (D) adds one more L. TODO(hw): the same on a real hub.
